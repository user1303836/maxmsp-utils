My M4L API research is complete. Full findings at `/Users/user1303836/Development/maxmsp-utils/.research/m4l_api_research.md`. Here are the key findings relevant to your review of sequencer engine/timing/data architecture:

**Critical findings:**

1. **live.remote~ for output**: Accepts 0-1 normalized signal input, maps to any DeviceParameter. Has ~1 audio buffer latency. TAKES OVER the parameter (user loses manual control). CPU scales linearly per instance — design should minimize active instances.

2. **live.modulate~ as alternative**: Does NOT take over the parameter, shows modulation ring, input -1 to 1 as offset. Better UX for modulation outputs. Consider this for AUX/CV outputs instead of live.remote~.

3. **MIDI multi-channel limitation**: Live converts all MIDI to channel 1 internally. Multi-channel output only works to external hardware. MPE within Live requires sender/receiver device pattern across multiple tracks.

4. **Parameter count**: No hard limit documented. ~391 params feasible but MUST use "Stored Only" for bulk step data (~300+ params) to avoid undo buffer overload and automation clutter. Keep "Automated and Stored" to ~30-50 max.

5. **Initialization**: loadbang fires BEFORE Live API is ready. MUST use live.thisdevice for any Live API calls. Use ONE loadbang with triggers for non-API init.

6. **Path resolution**: `goto live_set tracks N devices N parameters N` (0-indexed). Returns `id 0` for missing targets — must always check. Use Persistent Mapping for surviving save/load.

7. **Push/live.banks**: 8 params per bank, no max bank count. ~49 banks for 391 params is a lot — recommend only banking the most important controls.

No absolute showstoppers found, but the MIDI multi-channel limitation and live.remote~ CPU overhead need careful architectural consideration.

My Max 9 / MSP research is complete. Full findings are at /Users/user1303836/Development/maxmsp-utils/.research/max9_sequencer_features.md

Key findings that will impact the implementation plan:

1. **CRITICAL - New Step Sequencer Objects:** Max 9.1 added `stepfun~`, `stepdiv~`, and `stepcounter~` — purpose-built signal-rate step sequencer primitives. These can dramatically simplify the sequencer engine. `stepcounter~` directly supports variable pulse counts per stage (the `seq` attribute takes a list like "2 1 3 1"), `stepdiv~` subdivides a master phasor into per-step phasors, and `stepfun~` generates value sequences with curve control. The plan should evaluate whether these replace custom gen~ clock logic.

2. **Clock source:** `phasor~ 16n @lock 1` is the recommended clock — syncs to Live transport at signal rate. `plugsync~` is good for transport state (play/stop, tempo, time sig) but its beat output has ~1.5ms jitter.

3. **v8 JavaScript CANNOT be used for timing-critical code** — it runs ONLY in the low-priority thread. Use v8 for UI, presets, config only. Core sequencer clock/step advancement must be in patcher objects, gen~, or the new step objects.

4. **Slide/portamento:** `slide~` is the standard approach (logarithmic smoothing with separate up/down rates). Custom gen.codebox~ can do linear or exponential curves if needed. No specific ABL object needed.

5. **pattrstorage with 391 params:** Should be fine. Use single root-level pattrstorage + autopattr + changemode 1. Avoid nesting. Preset interpolation now supported with float recall.

6. **MC objects not recommended** for dual-track architecture — tracks have different behavior/config. Use separate subpatchers.

7. **`schedule` object (Max 9):** Route MIDI output through this for scheduler-thread timing precision.

8. **array.* objects:** Good for UI/config state storage (stage pitches, velocities, scale definitions). For signal-rate lookup during playback, use buffer~+index~ or gen~ data/peek.
